### まちがいさがし内蔵4題と画像制作ルール(2026-08-22、公開済み)

- 内蔵サンプルへ **むしの おにわ / よるの むしのもり / おしろの プリンセス / うみの いきもの** を追加した。各題は元絵1枚・差分絵1枚・スポット5件で、画像は `assets/samples/diff-*-base.jpg` / `diff-*-v1.jpg` の1200×800
- 最初は花芯や幼虫の小丸など、小さい色替えが多く幼児向けの差分として弱かった。最終版は **形・種類・個数・体節・腕や触手の数** を中心にし、色だけの変更は1題につき最大1か所、かつ十分な面積がある場所だけにした
- 例: 花→チューリップ、三日月→満月、どんぐり→松ぼっくり、バラ→チューリップ、尖り屋根→丸屋根、鳥の数、髪型、ヒトデやタコの腕数。むしの おにわのトンボの尾色、プリンセスの腰リボン色だけは色差として残した
- 虫の白目・瞳の光沢とクワガタの擬人化した顔を削除。背景を含めて均一に描き込みすぎず、主役だけ読みやすく、背景は線・葉・地面テクスチャを減らす
- プリンセス右上の空に浮いていたタペストリーは、間違いには数えず元絵・差分絵の両方から削除した
- 画像生成は **元絵を先に確定し、その元絵を編集対象として差分絵を作る**。左右を別々に新規生成すると、指定外の線・質感・配置まで変わるので不可。画像生成後も、元絵へ指定した5領域だけをぼかしマスクで合成すると、6個目以降の意図しない違いを防げる
- スポットの `r` は画像幅基準で、タッチ判定はさらに `1.35倍`。縦方向も画像幅基準の円になるため、近接する差分は見た目以上に重なりやすい。プリンセスの髪とリボンは、中心を離して拡張後の判定円にも隙間ができる半径へ修正した(`sampleRevision: 3`)
- 公開後に内蔵画像や座標を直す場合は、同じIDの `sampleRevision` を上げる。`Store.ensureSamples()` が既存端末のIndexedDBを同じIDで更新するため、題名の重複を出さず修正版へ差し替えられる
- 4題ともタッチ5か所で `みつけた: 5 / のこり: 0`、既存端末相当のIndexedDB更新、1200×800、EXIFなし、ブラウザエラーなしを確認した。画像変更だけでも `core.js` のスポット・`sampleRevision`・全HTMLの `?v=` を一緒に確認する

### フォント・演出文字・操作文言の整理(2026-09-02、公開)

- 基本文字は Google Fonts の **M PLUS Rounded 1c**、演出文字は **Mochiy Pop One** を採用。会場のオフライン環境でも崩れないよう、WOFF2を `assets/fonts/` へ同梱した
- 演出文字は背景フレームを使わず、最大64px・細い明縁・控えめな影に変更。小さい状態からフェードしながら拡大し、少し拡大しながらフェードアウトする。連続メッセージは前の表示を消して重ならない
- 「かち！ +○てん」「クリア！ ○びょう」のような複合表示をやめ、感情を伝える短い演出と、消えない結果カード／HUDの数値に分離した
- リレーの「タッチ！」は白塗りをやめ、濃い茶色+細い明縁へ変更。ゴール・実況テロップも一文一動作へ短縮した
- 選択確定は「きめた！」、同条件の再挑戦は「もういちど」、選択やチーム分けへ戻る操作は「やりなおす」に統一。色は緑=進む／再挑戦、黄=選び直す／リセット、青=補助操作を基本とした
- 事前提案は `design/ui-feedback-audit.html` / `.png`、フォント比較は `design/font-candidates.html` / `.png` に保存した(`design/` はPages非公開)
- `tools/build-pwa.mjs` の公開拡張子へ `.woff2` を追加し、フォント4ファイルがオフラインキャッシュへ入ることを確認した

## 2. アプリ化について(検討済み・未着手)

### 結論

**Web を正とし、アプリはガワ(WKWebView か Capacitor)にする。** 今の HTML をそのまま同梱すれば、同じコードで iOS・Android の両方を出せる。

オーナーは Mac・Xcode・Apple Developer Program を持っているため、コスト面の障害はない。

### アプリでしか取れない利点

| 項目 | ブラウザ + ホーム画面追加 | ネイティブアプリ |
|---|---|---|
| 他の人・別端末への配布 | 「Safariで開いて→共有→ホーム画面に追加」を毎回説明する必要がある | App Store で「入手」を押すだけ |
| 横画面の強制 | **iPad Safari では不可**(ページから画面を回せない) | `Info.plist` で横向き固定。確実 |
| 販売・課金 | 不可 | StoreKit で完結 |
| オフライン | Service Worker のキャッシュ次第(事前に一度オンラインで開く必要あり) | インストール時点で同梱、依存ゼロ |

とくに「全画面ボタンで自動的に横画面」は iPad Safari ではどう書いても実現できない。今は代わりに、縦画面のとき「よこむきに すると 大きく 見えるよ」の帯を出している(`js/core.js` の `Rotate`)。

### 進めるときの注意

- **ガイドライン4.2(最低限の機能性)** … 単なる Web サイトのラッパーは弾かれることがある。「コンテンツを同梱して完全オフラインで動く」は有効な反論材料
- **キッズカテゴリ** … third-party 解析・広告は不可、外部リンクにはペアレンタルゲート、プライバシーポリシー必須。このアプリは通信を一切しないので書きやすい
- **データは移行されない** … ブラウザの IndexedDB とアプリ内ストレージは別物。本番で使う写真・クイズは「使うほうで」作るか、`admin.html` の zip 書き出し/読み込みで移す
- **イベント当日の必須条件ではない** … 当日は今の Web 版 + 画面の向きロック + アクセスガイドで戦える。アプリは配布・販売を見据えた別プロジェクトとして進めるのが安全

### 検証のやり方(Playwright)

実機がないので、Chromium をタッチありで動かして確認している。

```js
chromium.launch({
  executablePath: '/opt/pw-browsers/chromium-1194/chrome-linux/chrome',
  args: ['--no-sandbox', '--disable-gpu'],   // --no-sandbox が無いとハングする
});
browser.newContext({ viewport: {...}, hasTouch: true, isMobile: true });
```

よく使うサイズ:

| サイズ | 何 |
|---|---|
| 1194x834 | iPad 横(本番) |
| 834x1194 | iPad 縦 |
| 740x360 | スマホ横 |
| 393x800 | スマホ縦 |

はまりどころ:

- `--no-sandbox` を付けないとブラウザ起動でハングする
- node の stdout をパイプに流すとバッファされて途中経過が見えない。**ログはファイルに書く**
- ページを開いた直後はサンプル画像の生成が重い。**2秒ほど待ってから**操作する
- レイアウトの重なりは目視より `elementFromPoint` で測るほうが速い(PR #30 の戻るボタンはこれで原因が分かった)
