### つくる画面まわりの構成(このセッションで変更)

```
index.html ──「つくる」タブ─→ create.html(4つの入口だけ)
                                 ├─ admin.html?from=create        とりこみ
                                 ├─ draw-pick.html?from=create    おえかき(なにを かく? + いちらん)
                                 │     └─ draw.html?kind=..&back=..
                                 ├─ create-quiz.html              ４たくクイズ

                                       └─ draw.html?cat=pic&back=..
```

- **`Nav._closeOverlay` が「もどる」を食べていたのを修正**(`js/core.js`)。
  `document.querySelector(".picker, .modal")` が editors.js の **hidden なモーダル** まで拾い、
  「モーダルを閉じた」つもりで `true` を返すため、`create.html`・`admin.html` で
  戻るボタンが何も起きなかった。`:not(.hidden)` を足しただけの1行修正
- **`Guide`(`js/core.js`)** … おえかきの「あたり」の定義。何を描くか(にんげん/スカート/どうぶつ/
  ちょうちょ/ふわふわ/かお/はいけい)ごとに、紙の縦横比・保存先・うごきのタイプ・点線の形・一言を持つ。
  点線の位置は `Rig.DEFAULT`(くび0.42・こし0.70・まんなか0.5・おなか0.55)に合わせてあるので、
  **あたりに沿って描けば うごきせっていを触らなくても正しく動く**
- **`Editors.mountLists`(`js/editors.js`)** … 「1行=1まいの絵+編集ボタン」の一覧を各ページで共通化
- **`create.html` はトップの「つくる」タブそのもの** … `index.html` と同じ体裁で出す
  (みだしバーなし・ロゴ・同じタブ列・右上のせっていボタン)。そのため
  `.logo` / `.subtitle` / `.settings-bar` / `.settings-fab` / `.tab-undoukai` は
  index.html のインラインCSSから `css/style.css` へ移した(2ページで共有するため)。
  `.tiles.four` の幅もトップのゲーム一覧と同じ 980px にして、右上のボタンと右はしをそろえてある
- **`draw.html` の `?back=`** … 戻り先。飛び先を勝手に増やさないよう `BACK_PAGES` の
  ホワイトリストでしか受け付けない。ページを増やしたらここに足すこと

## 2. アプリ化について(検討済み・未着手)

### 結論

**Web を正とし、アプリはガワ(WKWebView か Capacitor)にする。** 今の HTML をそのまま同梱すれば、同じコードで iOS・Android の両方を出せる。

オーナーは Mac・Xcode・Apple Developer Program を持っているため、コスト面の障害はない。

### アプリでしか取れない利点

| 項目 | ブラウザ + ホーム画面追加 | ネイティブアプリ |
|---|---|---|
| 他の人・別端末への配布 | 「Safariで開いて→共有→ホーム画面に追加」を毎回説明する必要がある | App Store で「入手」を押すだけ |
| 横画面の強制 | **iPad Safari では不可**(ページから画面を回せない) | `Info.plist` で横向き固定。確実 |
| 販売・課金 | 不可 | StoreKit で完結 |
| オフライン | Service Worker のキャッシュ次第(事前に一度オンラインで開く必要あり) | インストール時点で同梱、依存ゼロ |

とくに「全画面ボタンで自動的に横画面」は iPad Safari ではどう書いても実現できない。今は代わりに、縦画面のとき「よこむきに すると 大きく 見えるよ」の帯を出している(`js/core.js` の `Rotate`)。

### 進めるときの注意

- **ガイドライン4.2(最低限の機能性)** … 単なる Web サイトのラッパーは弾かれることがある。「コンテンツを同梱して完全オフラインで動く」は有効な反論材料
- **キッズカテゴリ** … third-party 解析・広告は不可、外部リンクにはペアレンタルゲート、プライバシーポリシー必須。このアプリは通信を一切しないので書きやすい
- **データは移行されない** … ブラウザの IndexedDB とアプリ内ストレージは別物。本番で使う写真・クイズは「使うほうで」作るか、`admin.html` の zip 書き出し/読み込みで移す
- **イベント当日の必須条件ではない** … 当日は今の Web 版 + 画面の向きロック + アクセスガイドで戦える。アプリは配布・販売を見据えた別プロジェクトとして進めるのが安全

## 3. 積み残し(上から優先度順)

### すぐやれるもの

1. **進行アイコンの差し替え** — オーナーが用意予定。`undoukai.html` の `EVENTS[].icon` が唯一の参照元。`assets/buttons/{race,tamaire,dodgeball,relay}.png` を同名で置き換えるだけで入れ替わる。**実寸は30px(今の競技だけ36px)** なので、その大きさで潰れない絵が必要。デザインキャンバス用の96px縮小版が `design/undoukai/icons/` にあるので、そちらも差し替える(`build.py` で再生成 →キャンバスを再公開)
2. **たまいれの残り時間** — PR #29 で上の帯ごと消えたため、あそび中は残り時間が出ない。「そこまで!」のテロップと数え上げで区切りは分かるが、時間だけ小さく出したいなら右上か左上に1つだけ戻せる
3. **負けチームのセリフのバリエーション** — 今は「よく がんばった!」固定(`js/meet.js` の `celebrate`)。競技に応じて「おしかった!」等を回せる

### 中くらい

4. **競技ごとの決着のお祝い演出** — 今は総合結果でしか `Meet.celebrate` を使っていない。デザイン提案では競技ごとの決着でも勝者が跳ねて紙吹雪が出る想定。`undoukai.html` の結果カードの前に `Meet.celebrate` を挟む形になる
5. **キャラ名が canvas 上で重なる** — 元からの挙動。`js/meet.js` の各 `draw` でキャラの足元に名前を描いているため、キャラ同士が近いと名前が重なる。縦画面だと縮尺の関係でさらに読みにくい
6. **ちょうちょの「あたり」が ちょうちょに見えにくい** — はねを1まいだけ描く都合で、
   紙の左はしに からだの線・右がわに はね1まい という形になる。
   仕様どおりではあるが、初見だと「B」に見える。左に薄い鏡像を出せると分かりやすいが、
   はねのつけねが紙の左はしにあるため場所がない(紙の比率から見直す必要あり)
7. **スマホ縦でおえかきの紙が小さい** — 左の戻るボタンと右の「🎨 どうぐ」で108px使うため横幅で制限される。「どうぐ」を右下に寄せれば紙を1割ほど広げられる

### 大きいもの

8. **PWA 化(manifest + Service Worker)** — アプリ化が間に合わない場合の、当日のオフライン確実性の担保。全ファイル約11MBを事前キャッシュ。ホーム画面に追加すれば Safari の7日間データ削除の対象外にもなる。1〜2時間の作業
9. **アプリ化本体** — 上記2章

## 4. 本番当日の運用メモ

- **画面出力は HDMI アダプタの有線で。** AirPlay は Wi-Fi が要るので会場では使えない
- 自動ロック「なし」、集中モード ON、画面の向きをロック(横)
- **アクセスガイド**(設定→アクセシビリティ)を使うと、子どもが触ってもホームに戻れない
- 前日に**機内モードにして全ゲーム通しリハーサル**。これが一番確実な検証
- **直前に修正したら、必ず家の Wi-Fi で一度開いてから持ち出す。** `?v=` の更新はオンラインで開いたときに反映される

### 検証のやり方(Playwright)

実機がないので、Chromium をタッチありで動かして確認している。

```js
chromium.launch({
  executablePath: '/opt/pw-browsers/chromium-1194/chrome-linux/chrome',
  args: ['--no-sandbox', '--disable-gpu'],   // --no-sandbox が無いとハングする
});
browser.newContext({ viewport: {...}, hasTouch: true, isMobile: true });
```

よく使うサイズ:

| サイズ | 何 |
|---|---|
| 1194x834 | iPad 横(本番) |
| 834x1194 | iPad 縦 |
| 740x360 | スマホ横 |
| 393x800 | スマホ縦 |

はまりどころ:

- `--no-sandbox` を付けないとブラウザ起動でハングする
- node の stdout をパイプに流すとバッファされて途中経過が見えない。**ログはファイルに書く**
- ページを開いた直後はサンプル画像の生成が重い。**2秒ほど待ってから**操作する
- レイアウトの重なりは目視より `elementFromPoint` で測るほうが速い(PR #30 の戻るボタンはこれで原因が分かった)
